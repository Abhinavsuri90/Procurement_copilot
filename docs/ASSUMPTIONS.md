# Assumptions

Where the policy or data is ambiguous, the conservative reading was taken. Each assumption is encoded in
`src/policy/rules.yaml` / `src/policy/engine.py` and covered by tests; eval labels that depend on one say so.

| # | Assumption | Why | Where |
|---|---|---|---|
| A1 | The reference date is the one stated in `procurement_policy.md` (2026-09-30), parsed from the document; `AS_OF_DATE` overrides it. The wall clock is never used. | The starter README requires the policy's snapshot date. | `src/config.py` |
| A2 | "Exceeds available budget" means `cost > available`; a cost equal to the available amount is within budget. If a snapshot's `annual − committed ≠ available`, the smaller figure is used. Purchase history is context only (`committed_usd` already includes commitments; summing history would double count). | Plain reading of §2; conservative on inconsistent data. | `check_budget` |
| A3 | A security assessment is current on days 0–364 after its review date and **expired from day 365**. When the registry and the risk service disagree on the date, the older date decides. | "Current for 365 days from its review date" — the stricter of the two readings. | `assess_vendor` |
| A4 | A missing, `unknown` or unrecognised data-access level is treated as sensitive: Security review, and Privacy/Legal where the vendor region makes that relevant. It is also reported as missing information when absent. | §1 requires the field; §10 forbids assuming a favourable status. | engine §5–§7 |
| A5 | The policy defines no hard blocks. A vendor whose security status is `rejected`/`failed`/`blocked` is treated as a block (`recommend_reject`); everything else escalates instead of rejecting. Overlap and budget shortfalls are never rejections. | §3 "not an automatic rejection"; §2 routes shortfalls to a Finance exception. | `POL-5.VENDOR_REJECTED` |
| A6 | If the vendor's data region cannot be verified (service unavailable or no record) and the data is sensitive, Privacy review is added. | §6 "sensitive data *may* be stored outside the region" + §10 "do not infer a favourable status". | `POL-6.REGION` |
| A7 | Legal's "material data-processing or cross-region issue is identified" applies when personal (or unknown) data goes to a vendor that stores data outside the region. | §7 wording; NeuralDesk/GrowthForge cases. | `POL-7.CROSS_REGION` |
| A8 | "Department Head" is the nearest Director-or-above in the requester's reporting line, never the requester (E003/E005 → E007 Go To Market; a Director's head is their VP). | `employees.csv` has no department-head column; self-approval must be impossible. | `Repository.department_head` |
| A9 | The request's `annual_cost_usd` is the annualised amount (including "one-time annual" packages). The tier boundaries are inclusive at the top: $1,000.00 → T1, $10,000.00 → T2, $25,000.00 → T3. Legal's new-vendor rule is inclusive at $10,000 ("$10,000 or more"). | Table wording in §4 and §7. | `rules.yaml` thresholds |
| A10 | A vendor is "new" if it is absent from the registry or its procurement status is not `Approved`. | No other definition in the data. | `assess_vendor` |
| A11 | Every purchase needs a human approval (§11), so the starter contract's `human_review_required` is always true; `human_handoff.required` additionally marks requests that need specialist/exception review beyond routine sign-off (escalation floor). | Two different questions in the brief: who signs vs. whether to escalate. | `src/solution.py`, guardrails |
| A12 | Fit of an existing tool is a judgement for the AI; code only surfaces candidates (same product/vendor/category, keyword/synonym overlap). The catalog has no owner column, so a redirect's next step is owned by Procurement. | Design principle: AI interprets, code computes. | `search_existing_tools` |
| A13 | Facts are taken only from structured request fields and tool outputs; values mentioned only in free text (e.g. "about $5k") are not used — the field is reported missing and the requester is asked. | Prevents injected or ambiguous text from changing thresholds. | `collect_facts` |
| A14 | Injection detection is a deterministic pattern scan over request text and tool outputs; a hit never changes approvals, it adds `prompt_injection_detected` (high) and forces a human handoff. | §9 + escalation floor. | `src/agents/injection.py` |
